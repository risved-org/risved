# v0.24.0 — Monorepos, shared domains, and safer pruning

## Monorepo apps

Choose **App directory** in project creation, repository import, or **Project settings → Source**. Use a path such as `apps/web`; leave it empty for the repository root. The HTTP API accepts `root_directory`, and MCP project creation accepts `rootDir`. Saved app directories are retained for deploys, rebuilds, webhooks, and previews.

Workspace detection supports Bun, pnpm, npm, and Yarn. Install from the workspace root, then build the selected app and its local dependencies in dependency order. Build overrides run in the selected app directory. Workspace runtime images retain the workspace tree and dependency links. The selected Node/Bun runtime, Adonis Node 24 working directory, and React Router server-output guard are preserved.

## Deployment protection during manual pruning

Manual image, container, volume, build-cache, and full pruning wait until active builds, previews, and rollbacks finish, including health checks and failure cleanup. New deployments wait while a manual prune runs. Multiple builds can still run concurrently across projects; queued prunes get a turn before later builds. This coordination applies inside the Risved control-plane process; manually running Docker commands outside Risved is not coordinated.

## Metrics and cleanup fixes

Resource collection now samples running containers even while a newer deployment builds or has failed, avoids overlapping collection, and retains bandwidth baselines when a database write fails. One project's metrics failure no longer skips other projects. Disk-pressure checks use Docker's data root when available. Docker logging explicitly selects the compatible log driver, prune failures are surfaced, and repository selection/search responses are protected against account changes and stale requests.

## Shared domains with path routing

Multiple Risved apps can now share a hostname. Give the main app `onui.com` with prefix `/` and Blogomat the same hostname with prefix `/blog`. The longest matching path prefix wins: `/blog` matches `/blog` and `/blog/story`, while `/blogger` falls back to the root app.

Domain mappings expose a forwarding mode in the domain form and API. Preserve sends `/blog/story` upstream unchanged; strip sends `/story`. Query strings, methods, request bodies, streaming responses and WebSocket upgrades continue through Caddy. Risved overwrites `X-Forwarded-Prefix` with the configured mount path.

Proxy updates, deployment, rollback, recovery and removal retain each mapping's prefix and mode. Hostname/prefix pairs must be unique. Updating or removing one prefix preserves sibling mappings; automatic `www` redirects also respect mounts and explicit app routes. TLS remains hostname-based. Project, dashboard and deployment links retain the public mount prefix.

## Upgrade

Back up the Risved database before upgrading. The existing deployment migration step applies `0009_domain_paths`, preserving domain records while adding `/` and `preserve` defaults and replacing hostname-only uniqueness with hostname/prefix uniqueness. No live mappings need to be edited for existing behavior to continue. The journal retains the v0.23.0 MCP migration `0008` unchanged and registers routing migration `0009` immediately afterward with a later timestamp. Additive migration `0010_app_directory` then adds nullable `projects.root_directory`. Existing projects continue deploying from the repository root. Upgrade tests apply the journal exactly once and preserve existing domains and MCP credentials.

Blogomat must support its public mount at `https://onui.com/blog`: configure URL generation, redirects, asset paths, authentication callbacks and cookie paths accordingly. Prefix stripping alone does not make a root-hosted app subpath-compatible. Risved does not rewrite HTML.

See [path-routing configuration and verification](../path-routing.md) for API examples and staging checks covering the homepage, nested stories, static assets and POST requests. Automated proxy checks use fixture upstreams; Blogomat compatibility and real DNS/TLS issuance still require staging validation.
